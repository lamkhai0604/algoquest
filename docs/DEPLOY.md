# Deployment Runbook — AlgoQuest

Status: first deployment (T-307), approved by the PO on 2026-11-09. Hosting follows D-037; free tiers only (D-006).

| Part | Host | Plan | Notes |
| --- | --- | --- | --- |
| Frontend | Vercel | Hobby | Static build of `frontend/`; all paths serve `index.html` (`frontend/vercel.json`) |
| Backend | Render | Free web service | Docker build from `backend/Dockerfile` (`render.yaml`); 512 MB, sleeps after 15 minutes idle, about a minute to wake |
| Database | Neon | Free | Scales to zero; Flyway creates the schema at backend start |

No step needs a payment method. If any service asks for one, stop and ask the PO (D-006).

## Order

The backend URL is needed by the frontend and the OAuth apps, and the frontend URL is needed by the backend, so the steps run in this order:

1. Database (Neon)
2. Backend (Render), with a temporary frontend URL
3. Frontend (Vercel)
4. Production OAuth apps (Google, GitHub)
5. Final backend settings and a live smoke check

Secrets are typed only into the provider dashboards. They are never committed, pasted into issues or pull requests, or shared in messages.

## 1. Database — Neon

1. Create a project named `algoquest`, Postgres 16 or later, region **AWS US West 2 (Oregon)** (close to the Render region).
2. Open **Connect**, turn **Connection pooling off** (Flyway needs a direct connection), and read the connection details: host, database, user, password.
3. Build the JDBC URL from the host and database:

   ```text
   jdbc:postgresql://<host>/<database>?sslmode=require
   ```

   The user and password go into separate variables, not into the URL.

## 2. Backend — Render

1. **New → Blueprint**, connect the GitHub repository, branch `main`. Render reads `render.yaml` and creates the web service `algoquest-api` on the free plan.
2. Fill in the variables Render asks for:

   | Variable | Value |
   | --- | --- |
   | `DATABASE_URL` | JDBC URL from step 1 |
   | `DATABASE_USERNAME` / `DATABASE_PASSWORD` | Neon user and password |
   | `FRONTEND_URL` | Temporary: `https://example.com` (replaced in step 5) |
   | `OWNER_EMAIL` | The PO's sign-in email (first Owner, FR-17) |
   | `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | Temporary: `not-configured` (replaced in step 4) |
   | `GITHUB_CLIENT_ID` / `GITHUB_CLIENT_SECRET` | Temporary: `not-configured` (replaced in step 4) |
   | `GEMINI_API_KEY` | The Gemini key |

   `JWT_SECRET` is generated by Render. `GRADING_PROVIDER` is `gemini`.
3. Wait for the first deploy, then open `https://<backend-host>/actuator/health`. Expected: `{"status":"UP"}`. Note the backend URL, for example `https://algoquest-api.onrender.com`.

Deploys run automatically after each merge to `main`, once the GitHub checks pass (`autoDeployTrigger: checksPass`).

## 3. Frontend — Vercel

1. **Add New → Project**, import the repository, **Root Directory** `frontend`. The framework (Vite) and build settings come from `frontend/vercel.json`.
2. Add the environment variable `VITE_API_URL` = backend URL from step 2 (no trailing slash), for Production.
3. Deploy. Note the production URL, for example `https://algoquest.vercel.app`.

Pushes to `main` deploy to production. Other branches create preview deployments; previews cannot sign in, because the backend allows only the production origin.

## 4. Production OAuth apps

The local apps stay as they are. Production uses separate apps so local and production secrets never mix.

**Google** (Google Cloud console, same project as the local client):

1. **APIs & Services → Credentials → Create credentials → OAuth client ID**, type **Web application**, name `AlgoQuest (production)`.
2. **Authorized redirect URIs**: `https://<backend-host>/login/oauth2/code/google`
3. Save the client ID and secret into Render (`GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`).
4. While the consent screen is in **Testing**, only listed test users can sign in. Add each tester's Google account under **Audience → Test users**.

**GitHub** (Settings → Developer settings → OAuth Apps → New OAuth App):

1. Name `AlgoQuest`, homepage URL = frontend URL, **Authorization callback URL** = `https://<backend-host>/login/oauth2/code/github`.
2. Generate a client secret and save both values into Render (`GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`).

## 5. Final settings and live smoke check

1. In Render, set `FRONTEND_URL` to the frontend URL from step 3 (no trailing slash). Saving the variables redeploys the backend.
2. Live smoke check, in a private browser window:

   | # | Step | Expected |
   | --- | --- | --- |
   | 1 | Open the backend health URL | `{"status":"UP"}` (the first request may take about a minute) |
   | 2 | Open the frontend URL | Sign-in page; a refresh on any path still loads the app |
   | 3 | Sign in with Google | Level map; the account is Owner (Admin link in the header) |
   | 4 | Sign out, sign in with GitHub | Level map |
   | 5 | Open Level 1, read the lesson, explain one Easy problem | A score and feedback from Gemini; XP on the bar |
   | 6 | Open Profile and Admin → grading log | Totals and streak; the attempt from step 5 with `gemini` as grader |

3. Record the result in the Sprint 3 report and close T-307.

## Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| Google shows `redirect_uri_mismatch` | Redirect URI differs from the backend host, or uses `http` | Copy the exact URI from the error into the OAuth client; the backend trusts the proxy's `X-Forwarded-Proto` (`server.forward-headers-strategy`) |
| Sign-in returns to the frontend with an error | `FRONTEND_URL` has a trailing slash or the wrong host | Fix the variable in Render |
| Browser console shows a CORS error | `FRONTEND_URL` does not match the page's origin exactly | Fix the variable in Render |
| Backend fails at start with a Flyway or connection error | Pooled Neon host, or the user and password inside the URL | Use the direct host and the JDBC form from step 1 |
| Backend restarts with out-of-memory errors | 512 MB limit | Check the Render logs; the image already uses small-memory JVM settings |
| Grading answers "unavailable" | `GEMINI_API_KEY` missing or the free quota used up | Check the variable; the quota resets daily |

## Rollback

- **Frontend:** Vercel → Deployments → choose the previous production deployment → **Promote to Production**.
- **Backend:** Render → Events → choose the previous deploy → **Rollback**. Migrations so far (V1 to V9) only add tables, columns, and indexes, so the previous version still runs on the newer schema. Check this again before rolling back over a migration that removes or renames anything.
